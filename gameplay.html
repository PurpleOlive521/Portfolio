Target Locking

What is it?

An ActorComponent that allows the camera to track enemies, locking onto them and keeping the screen centered when requested by the player. It creates MotionWarping targets to help the player target enemies even without input, or correct their input to stay on target.

What does it do?

Switch Targets

Players can switch targets by inputting a direction on the camera controls. While testing, I found that it was more intuitive to pick targets based on their location in screen space, as opposed to distance between targets. An input to the right would therefore switch from the current target to the nearest enemy on it's right, as they appear on screen.

Aim assist

During playtesting, we found that it could be difficult to keep the players attacks on enemies during the chaotic combat. To help this, actions that involve movement or require targeting can request MotionWarping points to be placed. The played animations can then use these points to rotate towards the targets direction. Any Actor with a TargetLockableComponent is tracked within a certain distance.

Gameplay System Module

What is the goal?

I wanted to create a tool that could be used to create many kinds of gameplay, utilising some common types that each would represent systems that games feature. This would require a heavily modular set of tools and classes that could then be derived and expanded upon for different games and teams.

What is it?

Throughout development I ended up with four tools, that all can be used to author gameplay elements. These are derived from superclasses that define their base functionality and purpose, and allow us to encapsulate gameplay elements into reusable pieces for easier development. I took inspiration from Unreal's GameplayAbilitySystem when designing the module.

How did I make it?

GameplayEffects

Temporary modifiers that can be applied to a GameplaySystem. hey can modify attributes or GameplayTags, allowing them to represent buffs, debuffs or game effects such as burning or being poisoned.

GameplayTag System

Tracks the amount of each tag present allowing multiple sources to modify a GameplayTag. This allows for more complex game behaviours where a state like 'Poisoned' can be applied multiple times, and require more actions to get rid of.

Integrated Debug UI

The framework features a custom Debug widget that automatically displays key properties of a GameplaySystem. It has custom input bindings that allow designers to quickly toggle it on and off during gameplay, switch the displayed page and swap the displayed component. It all comes together to ensure that debugging and testing of gameplay elements is easy and visual, without needing to step through code at every step of the way.

Abilities

These represent the actions that can be performed by an character. Supports complex activation requirements, cancelling of in-action abilities, cooldowns giving full control over how actions interact with each-other and what they do. Used heavily in 'Access Acquired' to drive the hack-and-slash combat.

Attributes

Datasets are used to source entities stats from. These can be anything from health to damage multipliers - whatever is needed for your game. These are then loaded by a GameplaySystem which can be queried for their current values.

Networked Tank Battles

What is it?

As the game was made from the ground up, the game has a multitude of separate systems that I wrote to create the gameplay loop and core functionality. The game was designed with a strong separation between different layers of the engine, as seen below, to make development easier. A shared library is used for all role-independent implementations, minimising code duplication. I roll my own network protocol for the game. It handles automatic LAN discovery, connecting multiple separate clients, timeouts for unresponsive clients, disconnects and reconnects. Packets are sent from the Server 10 times per second, with Client sending input 20 times per second, but can be customised for different game types.

How did I make it?

Object-Oriented Design

The engine supports polymorphic handling of abstract GameObjects, which is the core Super class that all Game entities derive from. Objects can then implement multiple functions to expand their functionality, such as signing up to the TimeManager which Ticks objects and handles asynchronous actions and timers. GameObjects themselves don't handle networking logic, that handled in the Controller class. Controllers are assigned to objects on creation, and handle the objects replication & serialization, interpolation and - in the case of PlayerControllers - input.

Physics Engine

Game Entities can also participate in game collision handling. Colliders are used to describe physics shapes, which are represented as a collection of convex 2D points. Participating entities will receive callbacks when colliding with other entities and receive any generated collision data. I use Separating Axis Theorem to detect collisions between game-ticks. I then collect some initial collision data and resolve each collision separately. Minimum Translation Vector is used to accurately separate objects with respect to their position and rotation

Network Protocol

I roll my own network protocol for the game. It handles automatic LAN discovery, connecting multiple separate clients, timeouts for unresponsive clients, disconnects and reconnects. Packets are sent from the Server 10 times per second, with Client sending input 20 times per second, but can be customised for different game types.

Reliable Messages

Messages are always guaranteed to be received, and are stored and packed into the leftover empty space in packets. Each message is tracked, stored and resent in each packet until it is confirmed to be received by the other end. An algorithm is used to encode packet-level acknowledges into a uint32, allowing a single packet to describe the acknowledge state of 32 messages. Some messages will always need to be tracked, such as spawning of player-controlled objects so that connecting Clients can replicate them correctly. These so called 'Critical' messages are stored and later sent for any newly connected client. They can then be queried and removed in case the message is no longer valid, such as when a player leaves and their controlled object is removed.

Takeaways

The project allowed me to try my hand at implementing and designing a multitude of systems that we take for granted in the game engines we use today, such as physics, object handling and management, timers and more. I also got to learn how networking and net code is implemented in games, the complexities and issues that come with it, and how to address them.
