Target Locking

What is it?

An ActorComponent that allows the camera to track enemies, locking onto them and keeping the screen centered when requested by the player. It creates MotionWarping targets to help the player target enemies even without input, or correct their input to stay on target.

What does it do?

Switch Targets

Players can switch targets by inputting a direction on the camera controls. While testing, I found that it was more intuitive to pick targets based on their location in screen space, as opposed to distance between targets. An input to the right would therefore switch from the current target to the nearest enemy on it's right, as they appear on screen.

Camera Tracking

A CameraModifier is applied to the owning Actors Camera component, which is responsible for the target tracking and ensures only one tracking modifier is applied at once.

World-Icon

When a target is locked, a WidgetComponent is enabled and lerped towards targets location. It queries the targets TargetLockingComponent to allow it to decide the location of the icon to ensure that different-sized targets all have the icon centered on their body.

Aim assist

During playtesting, we found that it could be difficult to keep the players attacks on enemies during the chaotic combat. To help this, actions that involve movement or require targeting can request MotionWarping points to be placed. The played animations can then use these points to rotate towards the targets direction.

When an action requests a target, one is picked in the following order:
1. If there is active player movement input beyond a low threshold use the input.
2. If there is an active Target Lock, use its target.
3. Find the closest tracked target in the forward direction of the owning Actor.
4. Don't create a MotionWarping point.

The active-input-override was added during the implementation, since I noticed very quickly that whenever the aim assist tried to track a target my own input would be ignored which just felt frustrating, rather than helpful.

Finally, while I was at it I added an extra feature where whenever a target is found very close to the direction the player inputs, it will place a MotionWarping point on it to it to ensure the attack is facing the target.

Takeaways

• Aside from being very satisfying to tweak until it felt just right, it also helped improve game-feel and player agency.
• The screen-space-based selection for targets makes the controls much more intuitive, and is something I recommed more games do.
• Not many players used the Target Locking, so I would focus my time on the aim assist and other features if done again.

Gameplay System Module

What is the goal?

I wanted to create a tool that could be used to create many kinds of gameplay, utilising some common types that each would represent systems that games feature. This would require a heavily modular set of tools and classes that could then be derived and expanded upon for different games and teams.

What is it?

Throughout development I ended up with four base tools, that all can be used to author gameplay elements. These are derived from superclasses that define their base functionality and purpose, and allow us to encapsulate gameplay elements into reusable pieces for easier development. I took inspiration from Unreal's GameplayAbilitySystem when designing the module.

This module was used for creating the hack-and-slash combat featured in Access Acquired.

Abilities

These represent the actions that can be performed by an character. Supports complex activation requirements, cancelling of in-action abilities, cooldowns and more, giving full control over how actions interact with each-other and what they do.

GameplayEffects

Temporary modifiers that can be applied to a GameplaySystem. hey can modify attributes or GameplayTags, allowing them to represent buffs, debuffs or game effects such as burning or being poisoned.

Integrated Debug UI

The framework features a custom Debug widget that automatically displays key properties of a GameplaySystem. It has input bindings that allow designers to quickly toggle it on and off, switch the displayed page and swap the displayed component.

Attributes

These can be anything from health to damage multipliers - whatever is needed for your game. Modifiers can be aggregated and stacked which allows for complicated RPG-like stat chains of mixed types, such as additive, multiplicative or overriding effects.

Levels and experience

A DataSet can be used to assign level-breakpoints, which will trigger when enough experience is gained. This can increase attributes and trigger fitting visual effects.

Networked Tank Battles

What is it?

A fully networked game, ran over the local network with my own network protocol and game engine. It handles automatic LAN discovery, connecting multiple separate clients, timeouts for unresponsive clients, disconnects and reconnects. Packets are sent from the Server 10 times per second, with Client sending input 20 times per second, but can be customised for different game types.

Object-Oriented Design

The engine supports polymorphic handling of abstract GameObjects, which is the core Super class that all Game entities derive from. Objects can then implement multiple functions to expand their functionality, such as signing up to the Controllers are assigned to objects on creation, and handle the objects replication & serialization, interpolation and - in the case of PlayerControllers - input.

Physics Engine

Colliders are used to describe physics shapes, which are represented as a collection of convex 2D points. Participating entities will receive callbacks when colliding with other entities and receive any generated collision data. I use Separating Axis Theorem to detect collisions between game-ticks. Minimum Translation Vector is used to accurately separate objects with respect to their position and rotation.

Ticking and Timers

TimeManager which Ticks objects and handles asynchronous actions and timers.

Network Protocol

It handles automatic LAN discovery, connecting multiple separate clients, timeouts for unresponsive clients, disconnects and reconnects. Packets are sent from the Server 10 times per second, with Client sending input 20 times per second, but can be customised for different game types.

Reliable Messages

Each message is tracked, stored and resent in each packet until it is confirmed to be received by the other end. An algorithm is used to encode packet-level acknowledges into a uint32, allowing a single packet to describe the acknowledge state of 32 messages. Some messages will always need to be tracked, such as spawning of player-controlled objects so that connecting Clients can replicate them correctly. These so called 'Critical' messages are stored and later sent for any newly connected client. They can then be queried and removed in case the message is no longer valid, such as when a player leaves and their controlled object is removed.

Takeaways

The project allowed me to try my hand at implementing and designing a multitude of systems that we take for granted in the game engines we use today, such as physics, object handling and management, timers and more. I also got to learn how networking and net code is implemented in games, the complexities and issues that come with it, and how to address them.
